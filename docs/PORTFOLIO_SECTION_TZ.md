# ТЗ: раздел Games для gamedev.land

## 1. Назначение документа

Этот документ фиксирует требования к новому разделу портфолио игр на сайте
`https://gamedev.land`. На его основе должен быть подготовлен отдельный implementation plan, а затем
выполнена реализация.

ТЗ описывает продуктовый результат, структуру контента, обязательные состояния интерфейса,
технические ограничения и критерии приемки. Оно не является implementation plan и не должно
подменять его перечнем файлов и мелких шагов разработки.

## 2. Цель раздела

Добавить на сайт единую витрину всех игр Александра Болотникова: выпущенных проектов, прототипов,
технических демо и архивных работ.

Раздел должен решать две задачи:

1. Дать посетителю быстрое визуальное представление о сделанных играх.
2. Для каждой игры предоставить отдельный case study с playable-версией, описанием проекта и
   техническими подробностями.

Раздел является частью существующего блога, а не отдельным промолендингом. Он должен сохранять
визуальную связь с текущим сайтом, но быть заметно более игровым и визуальным за счет реальных
иконок, обложек и скриншотов проектов.

## 3. Контекст текущего проекта

- Сайт реализован на Astro 6 без клиентского UI-фреймворка.
- Основной язык интерфейса и навигации сайта — английский.
- Верхнее меню сейчас содержит `Home` и `About`.
- Общие страницы используют `Layout.astro`, `Header.astro`, `Footer.astro` и стили из
  `src/styles`.
- На сайте уже используется Astro Content Collections для статей.
- Сайт публикуется на `https://gamedev.land`, а playable-сборки игр могут размещаться на
  `https://gamedevland.github.io/...`.
- Генерируемый каталог `dist/` не является исходным кодом и не должен редактироваться вручную.

## 4. Scope первой версии

### 4.1. Входит в MVP

- ссылка `Games` в верхнем меню;
- индексная страница `/games`;
- отдельная статически генерируемая страница `/games/[slug]` для каждой опубликованной записи;
- единый типизированный источник данных и подробного контента игр;
- карточки с реальными иконками или подготовленным fallback;
- playable-блок через iframe для игр, у которых есть совместимая web-сборка;
- внешняя ссылка на playable-сборку;
- описание игры, вклад автора, технологии, статус и доступные ссылки;
- адаптивность, keyboard navigation, базовая SEO-разметка и корректные состояния отсутствующих
  данных;
- проверка production build.

### 4.2. Не входит в MVP

- отдельная CMS или административная панель;
- поиск по портфолио;
- фильтры при небольшом количестве игр;
- рейтинги, комментарии, лайки и другая социальная функциональность;
- автоматический импорт данных из GitHub или игровых порталов;
- сбор игровой статистики внутри iframe;
- локализация всего раздела на несколько языков;
- тяжелый клиентский framework только ради карточек или фильтрации;
- обязательное создание новых иллюстраций, если в проектах уже есть подходящие реальные ассеты.

Фильтры можно вынести во вторую итерацию, когда в портфолио будет достаточно проектов, чтобы
ручное сканирование сетки стало неудобным.

## 5. Информационная архитектура

### 5.1. Маршруты

- `/games` — индексная страница портфолио;
- `/games/[slug]` — страница конкретной игры.

Маршрут `/games` является принятым решением для первой версии. Алиас `/portfolio` и redirect с него
не требуются, пока такой URL не использовался публично.

### 5.2. Верхняя навигация

Порядок ссылок:

1. `Home`
2. `Games`
3. `About`

Ссылка `Games` должна иметь активное состояние как на `/games`, так и на всех страницах
`/games/[slug]`. Текущие состояния `Home` и `About` не должны регрессировать.

### 5.3. Язык

Пользовательский интерфейс и контент первой версии оформляются на английском, чтобы соответствовать
существующей навигации и основным страницам сайта. Само ТЗ остается на русском.

Русская локализация может быть спроектирована отдельно. В MVP не нужно дублировать страницы или
смешивать два языка внутри одной карточки.

## 6. Состав портфолио

В первую версию должны войти как минимум:

- `Stickers Merge`;
- `Fish Sort`;
- `Block Puzzle` — рабочее название должно быть уточнено по фактическому названию проекта; в
  описании допустимо указать, что это Block Blast-style puzzle;
- `Hidden Pigeon`;
- другие завершенные игры, прототипы и демо автора, для которых удастся подтвердить минимально
  необходимые данные.

Перед implementation plan необходимо провести инвентаризацию доступных проектов и составить
контентную таблицу. Для каждой игры нужно подтвердить:

- официальное отображаемое название;
- slug;
- статус проекта;
- год или дату релиза, если они известны;
- короткое описание;
- роль автора;
- технологии;
- путь к иконке и другим доступным изображениям;
- URL playable-сборки;
- возможность загрузки этой сборки в iframe;
- публичные ссылки на репозиторий, статью или площадку, если они есть.

Нельзя угадывать даты, технологии, командный состав или публичные URL. Неизвестные данные должны
оставаться отсутствующими в модели, а не публиковаться как `TBD`. Черновая запись не должна попадать
в production-список до достижения минимальной контентной готовности.

## 7. Контентная готовность игры

### 7.1. Минимум для публикации карточки и страницы

- название;
- slug;
- короткое описание;
- подробное описание хотя бы из одного содержательного абзаца;
- статус;
- роль автора;
- минимум одна подтвержденная технология;
- иконка или согласованный визуальный fallback.

Playable URL и дата релиза желательны, но не обязательны. Отсутствие playable-версии не должно
исключать старую или архивную игру из портфолио.

### 7.2. Статусы

Нужно использовать ограниченный набор значений:

- `released` — опубликованная или завершенная игра;
- `prototype` — игровой прототип;
- `in-development` — активная разработка;
- `tech-demo` — техническое или учебное демо;
- `archived` — завершенный или остановленный старый проект без активной поддержки.

Человекочитаемые английские подписи статусов задаются централизованно и не дублируются вручную в
каждой записи.

## 8. Источник данных

Игры должны храниться в отдельной Astro Content Collection `games`. Каждая игра представляется
Markdown-файлом: frontmatter содержит структурированные данные, а body — подробный рассказ о проекте.

Это решение должно обеспечить:

- schema validation во время сборки;
- единый источник для карточки и detail page;
- удобное редактирование длинного описания;
- автоматическую статическую генерацию страниц;
- простое добавление новых игр без изменения page-компонентов.

### 8.1. Обязательные поля frontmatter

- `title: string` — отображаемое название;
- `description: string` — короткое описание для карточки и metadata;
- `status: enum` — одно из значений из раздела 7.2;
- `technologies: string[]` — подтвержденные технологии;
- `roles: string[]` — вклад и зоны ответственности автора;
- `iconImage: string` — путь к квадратной иконке;
- `iconAlt: string` — осмысленный alt-текст;
- `order: number` — ручной стабильный порядок на странице;
- `draft: boolean` — исключение незавершенной записи из production output.

Slug должен определяться именем Markdown-файла и не дублироваться отдельным полем без необходимости.

### 8.2. Опциональные поля frontmatter

- `releaseDate: Date` — только если известна точная дата;
- `releaseYear: number` — если известен только год; одновременно с `releaseDate` не используется;
- `genre: string`;
- `platforms: string[]`;
- `featured: boolean`;
- `coverImage: string`;
- `coverAlt: string`;
- `screenshots: { src: string; alt: string }[]`;
- `playableUrl: string`;
- `externalUrl: string` — внешняя страница игры, если она отличается от playable URL;
- `repositoryUrl: string`;
- `articleUrl: string`;
- `videoUrl: string`;
- `developmentPeriod: string`;
- `teamSize: string`;
- `orientation: 'landscape' | 'portrait' | 'adaptive'`;
- `embedAspectRatio: string` — проверенное соотношение сторон, например `16 / 9` или `9 / 16`;
- `embedAllow: string` — только реально необходимые iframe permissions.

`iframeUrl` отдельно от `playableUrl` добавляется только в случае, если embedded-сборка действительно
должна отличаться от версии, открываемой в новой вкладке.

### 8.3. Подробное описание в Markdown body

Описание не обязано следовать жесткому шаблону, но должно отвечать на вопросы:

- что это за игра и какова ее основная механика;
- для чего и в каком контексте она была сделана;
- что именно сделал автор;
- какие технологии и архитектурные решения использовались;
- какие особенности разработки или полученный опыт стоит выделить.

Пустые секции не выводятся. Если по старой игре сохранилось мало информации, лучше написать короткий
честный case study, чем заполнять страницу общими фразами.

## 9. Ассеты

### 9.1. Приоритет источников

1. Оригинальные иконки, splash screens и скриншоты из соответствующих игровых проектов.
2. Материалы с публичных страниц игры, если автор имеет право использовать их на своем сайте.
3. Подготовленный нейтральный fallback с названием или инициалами игры.

Не следует генерировать новую «похожую» иконку вместо существующего key art: портфолио должно
показывать реальную игру.

### 9.2. Организация файлов

Рекомендуемая структура статических файлов:

```text
public/assets/games/<slug>/
  icon.webp
  cover.webp
  screenshot-01.webp
```

- Иконка должна быть квадратной и иметь достаточное разрешение для четкого отображения на retina.
- Обложка и скриншоты должны иметь заранее оптимизированный размер и современный web-формат, если
  это не ухудшает качество.
- Размеры изображений должны быть зафиксированы в markup или CSS, чтобы избежать layout shift.
- Нельзя подтягивать ключевые изображения с временных внешних URL.

## 10. Индексная страница `/games`

### 10.1. Содержимое

- компактный header в рамках существующего `Header` с заголовком `Games`;
- короткое вступление о подборке released games, prototypes и technical demos;
- сетка всех опубликованных игр;
- footer существующего сайта.

Не нужно добавлять отдельный маркетинговый hero, статистику ради декора или длинное объяснение того,
как пользоваться страницей. Сетка игр должна начинаться в первом экране либо оставаться визуально
видимой у его нижней границы на типичном desktop viewport.

### 10.2. Карточка игры

Карточка целиком является семантической ссылкой на `/games/[slug]` и содержит:

- квадратную иконку как главный визуальный элемент;
- название;
- короткое описание;
- статус;
- год релиза, если известен;
- жанр, если известен;
- до трех ключевых технологий.

Карточка не должна напрямую запускать iframe или вести сразу на GitHub Pages: сначала пользователь
попадает на страницу проекта. Дополнительные данные не должны перегружать карточку.

### 10.3. Порядок

- Используется ручной порядок `order`, а не алфавитная сортировка.
- Сначала могут идти наиболее сильные или актуальные проекты.
- `featured` может влиять на визуальный размер карточки только при наличии убедительного макета и
  без нарушения scanability; в MVP достаточно порядка без отдельной featured-композиции.

### 10.4. Визуальное направление

Образ страницы — аккуратная коллекция игр, а не набор одинаковых блоговых карточек:

- реальные яркие иконки создают цвет, остальной UI остается спокойным;
- сетка плотная, ритмичная и легко сканируется;
- типографика и базовые цвета наследуют существующий сайт;
- игровые акценты используются умеренно и функционально;
- hover-анимация короткая и не меняет размеры сетки;
- интерфейс не строится на одном доминирующем акцентном цвете;
- карточки не вкладываются в другие карточки.

Ориентир для desktop: 3–4 карточки в строке в зависимости от итогового размера иконок. На tablet и
mobile сетка перестраивается без горизонтального скролла; на узком экране допускается 1–2 карточки
в строке после визуальной проверки.

## 11. Страница игры `/games/[slug]`

### 11.1. Верхняя часть

Первый экран должен быстро отвечать, что это за проект, и давать возможность сыграть:

- навигация назад к `Games`;
- иконка или cover;
- название;
- короткое описание;
- компактные metadata: статус, год, жанр и платформы — только доступные значения;
- playable-блок или понятное состояние `Playable build is not available`;
- команда `Open in new tab`, если задан playable URL.

Playable-блок является главным интерактивным элементом страницы, но не должен вытеснять название и
контекст проекта за пределы первого экрана на desktop.

### 11.2. Основной контент

- Markdown-описание проекта;
- секция `My role`;
- секция `Technologies`;
- доступные дополнительные факты: период разработки, команда, платформы;
- галерея реальных скриншотов, если они есть;
- ссылки `Source code`, `Read article`, `Watch video` или `View game page` только при наличии URL;
- ссылка назад к общему списку в конце страницы.

Не нужно автоматически создавать пустые секции и заглушки для каждого поля модели.

## 12. Playable iframe

### 12.1. Поведение

- iframe создается только при наличии проверенного playable URL;
- контейнер использует заданный для игры aspect ratio и имеет стабильные размеры до загрузки;
- для `adaptive`-игры используется проверенная высота/ограничение, обеспечивающее удобную игру;
- рядом доступна ссылка `Open in new tab` с `target="_blank"` и безопасным `rel`;
- fullscreen-control добавляется, если игра корректно поддерживает полноэкранный режим;
- loading state не должен перекрывать игру после события `load`;
- ошибка или запрет embedding не должны оставлять пользователя в тупике: внешняя ссылка остается
  доступной.

На mobile playable должен оставаться реально используемым. Для portrait-игр нельзя принудительно
использовать `16 / 9`; для landscape-игр нужно проверить читаемость контролов на узком экране.

### 12.2. Атрибуты и безопасность

Минимально требуются:

- уникальный понятный `title`;
- осознанный `loading` (`eager`, если iframe виден в первом экране, либо `lazy`, если он расположен
  ниже);
- `allowfullscreen`, если используется fullscreen;
- `allow` только для реально нужных возможностей, например fullscreen или autoplay;
- `referrerpolicy`, если это совместимо с аналитикой/SDK игры.

`sandbox` нельзя добавлять формально: сначала нужно проверить, не ломает ли он загрузку ассетов,
local storage, fullscreen, аудио, рекламу или SDK-интеграцию. Итоговый набор ограничений фиксируется
после проверки Block Puzzle и остальных playable-сборок.

### 12.3. Проверка embed-совместимости

Для каждого playable URL перед публикацией нужно проверить:

- отсутствие блокирующих `X-Frame-Options` и CSP `frame-ancestors`;
- загрузку ассетов с корректными путями;
- работу pointer/touch input и keyboard input;
- корректный resize внутри iframe;
- звук только после пользовательского взаимодействия;
- fullscreen, если заявлен;
- отсутствие явных ошибок в browser console;
- наличие внешней ссылки как резервного пути.

## 13. SEO и metadata

Для `/games`:

- уникальный `<title>`;
- уникальный meta description;
- canonical URL;
- Open Graph title, description, URL и image при наличии общего изображения раздела.

Для `/games/[slug]`:

- `<title>` на основе названия игры и `GameDev.Land`;
- description из короткого описания;
- canonical URL;
- Open Graph metadata;
- Open Graph image из cover или icon.

Если текущий `Layout` не поддерживает эти поля, его API следует расширить обратно совместимым
способом. JSON-LD типа `VideoGame` полезен, но не обязателен для MVP.

## 14. Доступность и UX

- Все карточки и команды доступны с клавиатуры.
- Для ссылок, кнопок и карточек есть заметный `:focus-visible`.
- Изображения имеют осмысленный `alt`; декоративные изображения используют пустой alt.
- Статус передается текстом, а не только цветом.
- Контраст текста и интерактивных элементов соответствует WCAG AA.
- Иконки и контент не меняют геометрию карточки при hover или загрузке.
- Учитывается `prefers-reduced-motion`.
- Touch targets имеют комфортный размер.
- На ширине 320 px нет горизонтального overflow, наложений текста и недоступных команд.
- Если JavaScript отключен, навигация, карточки, контент и внешняя ссылка на игру остаются рабочими.

## 15. Технические ограничения

- Использовать Astro pages/components и существующие design tokens.
- Не добавлять React, Vue, Svelte или другой UI runtime без отдельного обоснования.
- Не дублировать данные между индексной и detail pages.
- Валидировать collection schema на этапе сборки.
- Генерировать detail pages через `getStaticPaths`.
- Исключать `draft: true` из production-вывода и ссылок.
- Не редактировать `dist/`, `node_modules/` и другие generated artifacts.
- Не менять существующие статьи и unrelated sections без необходимости.
- Не добавлять зависимость ради функции, которую Astro или небольшой локальный компонент решает
  напрямую.
- Новый CSS должен продолжать существующую систему tokens, но отдельные portfolio-компоненты должны
  иметь собственные понятные class names.

## 16. Состояния, которые должны быть предусмотрены

- игра со всеми данными и playable iframe;
- игра без playable-сборки;
- игра без точной даты, но с годом;
- игра без даты вообще;
- игра только с иконкой, без cover и screenshots;
- игра с portrait embed;
- draft, не попадающий в production;
- несуществующий slug, обрабатываемый стандартным 404 Astro;
- iframe не загрузился или запрещен браузером, но внешняя ссылка доступна.

## 17. Критерии приемки MVP

### 17.1. Функциональность

- В top menu отображается `Games` в согласованном порядке.
- Активное состояние навигации корректно на `/games` и `/games/[slug]`.
- `/games` отображает все и только опубликованные записи collection `games` в ручном порядке.
- Каждая карточка ведет на существующую detail page.
- Для каждой опубликованной игры сборка генерирует отдельный URL.
- Playable iframe показывается только для игры с проверенным URL.
- Для игры без iframe выводится аккуратное информативное состояние.
- Все опциональные ссылки и секции скрываются при отсутствии данных.
- Ни на одной странице нет выдуманных фактов и видимых `TBD`.

### 17.2. Визуальное качество

- Реальные иконки являются главным визуальным сигналом индексной страницы.
- Desktop, tablet и mobile layouts не имеют горизонтального overflow и наложений.
- Карточки сохраняют стабильные размеры при загрузке изображений и hover.
- Portrait и landscape playable-сборки отображаются в подходящих пропорциях.
- Страницы выглядят частью существующего GameDev.Land, а не отдельным шаблоном.

### 17.3. Техническое качество

- `npm run build` завершается успешно.
- Внутренние ссылки не ведут на 404.
- Изображения не дают 404 и имеют alt-тексты.
- Страницы используют валидные title/description/canonical.
- Нет новых критичных ошибок browser console при проверке playable pages.
- Базовый сценарий полностью работает без клиентского JavaScript, кроме поведения самой embedded
  игры и необязательных enhancements.

## 18. Данные, которые нужны до implementation plan

Следующий этап должен начать с локальной инвентаризации, а затем зафиксировать недостающие данные у
владельца сайта. Нужны ответы или найденные источники для следующего:

- полный список игр первой версии;
- официальное название Block Puzzle / Block Blast-style проекта;
- GitHub Pages или другие playable URL;
- иконки, covers и screenshots;
- подтвержденные годы/даты релизов;
- краткое описание и роль автора по каждой игре;
- технологии по каждой игре;
- какие репозитории и внешние страницы можно публиковать;
- какие playable-сборки должны поддерживать fullscreen, audio, storage и SDK.

Отсутствие части необязательных данных не блокирует implementation plan: план должен явно отделить
разработку раздела от последующего наполнения контентом. Но для визуально полноценной первой версии
нужны реальные иконки минимум для четырех обязательных игр.

## 19. Требование к следующему этапу

Implementation plan должен:

1. Сначала провести инвентаризацию существующих проектов, ассетов, playable URL и текущих shared
   компонентов сайта.
2. Сформировать таблицу игр с состоянием готовности контента и списком неизвестных данных.
3. Разбить работу на проверяемые этапы: collection schema, shared metadata/navigation, компоненты,
   индексная страница, detail page, контент и ассеты, embed validation, responsive/visual QA, build.
4. Для каждого этапа указать конкретные файлы, зависимости от контента и способ проверки.
5. Не включать фильтрацию и другие post-MVP функции в основной путь реализации.
6. Отдельно отметить решения, которые нельзя принять без реальных ассетов или проверки playable
   builds.
